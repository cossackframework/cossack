# ORM Comparison

Cossack ORM is not intended to be a universal replacement for every TypeScript
database library. It is a focused choice for applications that want decorated
Active Record models, explicit relation loading, safe SQL, and runtime-specific
adapters—especially Cossack applications.

This page compares architecture and currently implemented features, not
benchmarks. “Yes” means the feature is part of the project's supported API; it
does not imply that every implementation has equal depth. “Manual” means the
result is possible with SQL or application code but is not modeled as a
first-class ORM feature.

Last reviewed: July 2026.

## Feature matrix

| Area | Cossack ORM | Drizzle ORM | TypeORM | Kysely | Prisma ORM |
| --- | --- | --- | --- | --- | --- |
| Primary abstraction | Decorated Active Record classes | TypeScript table schemas | Decorated entities with Active Record or Data Mapper | Typed SQL query builder | Prisma schema and generated client |
| Active Record methods | Yes | No | Yes | No | No |
| Repository/Data Mapper API | No, by design | No repository layer | Yes | No | Generated client, not a classic repository |
| Code generation required for queries | No | No | No | No | Yes |
| Typed SQL-style query builder | Yes, with some less precise complex join/projection types | Yes; a primary interface | Yes; entity-aware QueryBuilder | Yes; the primary focus | No general SQL builder; client API plus raw/TypedSQL |
| Relation metadata | Decorators and a serializable schema graph | TypeScript relation declarations | Decorators with extensive relation options | None in core | Prisma schema relations |
| Relation loading | Explicit `relations`/`with`; batched follow-up queries | Relational query API, normally one SQL statement | Explicit, eager, or lazy | Manual joins or application code | `include`/`select` and nested queries |
| Entity instances, hooks, and dirty tracking | Yes | No | Yes | No | Returns plain objects |
| Parameterized raw SQL | Fragment AST and tagged template | Tagged SQL templates | `sql` tag and lower-level query APIs | Tagged SQL templates | `$queryRaw`/`$executeRaw` and TypedSQL |
| Generated migrations | Yes; reviewable TypeScript, inverse must be written | Yes, through Drizzle Kit | Yes | Migration primitives; generation is not the core focus | Yes, through Prisma Migrate |
| Migration baseline | Built in | Possible through migration workflow | Manual migration-history workflow | Application-managed | Built in |
| Database introspection | SQLite, PostgreSQL, and MySQL adapters | Yes | Used for schema comparison; no first-party entity pull | Types commonly generated by external `kysely-codegen` | `db pull` |
| Model generation from a database | Decorated classes through `schema pull` | TypeScript schema through `pull` | Not built in | External code generator | Prisma schema through `db pull` |
| Runtime schema push/synchronization | No, by design | `push` available | `synchronize`/`schema:sync` available | No | `db push` available |
| First-party seeding support | Ordered `SeederRunner` with transaction policy | `drizzle-seed` data generator | Application or community tooling | Application code | CLI seed command runs an application script |
| SQL database coverage | SQLite, PostgreSQL, MySQL; D1 and libSQL adapters | Broad PostgreSQL, MySQL, SQLite, SingleStore, MSSQL, and CockroachDB ecosystem | Broad SQL driver set | Official PostgreSQL, MySQL, MSSQL, SQLite, and PGlite dialects | PostgreSQL, MySQL/MariaDB, SQLite, SQL Server, and CockroachDB |
| MongoDB/NoSQL | No | No | MongoDB support | No | MongoDB support |
| Edge/serverless focus | First-class Bun, D1, Hyperdrive, and injected Deno entry points | Strong, with many serverless drivers | Driver-dependent | Runtime-neutral; dialect/driver-dependent | Supported through driver adapters and supported deployments |
| Multiple connections | Multiple isolated `ORM` instances | Multiple database instances | Multiple `DataSource` instances | Multiple `Kysely` instances | Separate schemas/generated clients |
| Cross-database relations or transactions | No | No general cross-database unit of work | Limited multi-database querying; no general distributed transaction | No | No general distributed transaction |
| Maturity and ecosystem | New v1 package | Established ecosystem | Long-established, feature-rich ORM | Established and deliberately focused | Long-established ecosystem and tooling |

Database support in this table describes first-party, documented paths rather
than every community adapter. Capabilities still vary by driver. For example,
Cossack's D1 adapter supports atomic migration batches but not interactive
transactions or savepoints.

## Where Cossack ORM fits

Choose Cossack ORM when most of these are true:

- Entity classes should own persistence methods such as `find()`, `save()`, and
  `remove()`.
- Decorators are an acceptable source of schema metadata.
- Request-scoped Active Record calls should automatically participate in the
  current transaction.
- Relations should be requested explicitly and loaded in batches rather than
  hidden behind lazy properties.
- The same model layer must run through isolated Node, Bun, Cloudflare, or Deno
  adapters.
- Cossack Studio or other framework tooling needs serializable logical schema
  metadata, including virtual relations.

Do not choose it merely because it has a familiar API. The alternatives below
are stronger in several important areas.

## Compared with Drizzle ORM

Drizzle is a better fit for teams that think in tables and SQL and want strong
type inference close to the database. It has broader documented driver support,
a larger ecosystem, relational queries designed to compile to one SQL
statement, Drizzle Kit, Drizzle Studio, and a dedicated data-generation package.

Cossack adds stateful entity instances, decorators, lifecycle hooks, dirty
tracking, and Active Record methods. Its relation loader intentionally uses
batched follow-up queries, which can be easier to reason about across adapters
but may add round trips compared with Drizzle's relational query API. For
complex joins and calculated projections, Drizzle's types are currently more
complete.

Choose Drizzle for a SQL-first, schema-object workflow. Choose Cossack when the
entity class and its behavior should be the center of the application model.

See Drizzle's official [overview](https://orm.drizzle.team/docs/overview),
[migration workflows](https://orm.drizzle.team/docs/migrations), and
[relations documentation](https://orm.drizzle.team/docs/relations).

## Compared with TypeORM

TypeORM is the closest match in surface style: both use decorated entities and
support Active Record. TypeORM also supports Data Mapper repositories, eager
and lazy relations, more cascade and relation options, subscribers, additional
database families, schema synchronization, and other features accumulated over
a much longer lifetime.

Cossack is narrower. It has no repository layer, lazy relations, runtime schema
synchronization, query-result cache, or comparable extension ecosystem. In
return, it has an ESM-only package shape, explicit request/transaction scoping,
isolated runtime adapters, explicit batched relation loading, and a versioned
logical schema contract intended for framework tooling.

Choose TypeORM when feature breadth, database breadth, or Data Mapper is
important. Choose Cossack when its smaller Active Record-only model and
serverless/runtime boundaries align with the application.

See TypeORM's official [Active Record and Data Mapper
guide](https://typeorm.io/docs/guides/active-record-data-mapper/),
[relations reference](https://typeorm.io/docs/relations/relations/),
[migration generator](https://typeorm.io/docs/migrations/generating/), and
[multiple data source guide](https://typeorm.io/docs/data-source/multiple-data-sources/).

## Compared with Kysely

Kysely is a query builder, not an entity ORM. That is its advantage when a team
wants a thin, SQL-shaped abstraction with excellent composability and
compile-time result inference. It does not impose model instances, decorators,
relation loaders, dirty tracking, or lifecycle behavior.

Cossack's query builder covers common application queries, but Kysely is the
more capable and precise choice for deeply composed SQL, complex aliases, and
advanced projections. Cossack instead supplies the higher-level model and
tooling layers: Active Record, relation metadata, codecs, migrations,
introspection, generated models, and seed orchestration.

Choose Kysely when SQL and query typing are the product boundary and the
application will own its model conventions. Choose Cossack when those
conventions should be supplied by the ORM.

See the official [Kysely overview](https://www.kysely.dev/), which describes
its SQL-first scope, dialects, runtimes, migrations, and external code-generation
workflow.

## Compared with Prisma ORM

Prisma provides a mature schema language, generated type-safe client,
introspection, migration workflow, Studio, and broad ecosystem. Its records are
plain objects queried through `PrismaClient`; they are not Active Record
instances. The generated client and Prisma schema are intentional parts of its
workflow.

Cossack keeps the TypeScript entity class as the model source and does not
require client generation. It offers direct adapters, scoped static methods,
and a SQL-style builder, but it has fewer supported databases, less polished
tooling, and far less production history. Prisma is the safer default when its
schema/client workflow is acceptable and mature tooling matters more than
Active Record.

Choose Prisma for its generated-client workflow and established tooling. Choose
Cossack when decorated entity behavior, direct runtime adapters, and Cossack
framework integration are more important.

See Prisma's official [ORM overview](https://docs.prisma.io/docs/orm),
[supported databases](https://docs.prisma.io/docs/orm/reference/supported-databases),
and [Prisma Migrate guide](https://www.prisma.io/docs/orm/prisma-migrate/getting-started).

## Current Cossack limitations

The most important differences are not syntax:

- Cossack ORM is new. It does not yet have the production history, community
  integrations, or troubleshooting corpus of these alternatives.
- Its first-party database surface is intentionally smaller. SQL Server,
  CockroachDB-specific behavior, Oracle, MongoDB, and many specialized drivers
  are outside v1.
- Query types are strong for model properties and common operations, but
  complex raw joins, aliases, and computed projections can require explicit
  typing. Kysely and Drizzle are stronger for this work.
- Relation loading is explicit and batched, not lazy and not guaranteed to use
  one statement. TypeORM and Prisma support more relation behaviors; Drizzle
  can produce a single relational statement.
- Generated migrations require review, and generated `down()` methods must be
  implemented. There is deliberately no automatic startup synchronization.
- Automated integration coverage in this repository is currently strongest for
  Node SQLite. The runtime adapters and public contracts exist, but PostgreSQL,
  MySQL, Bun, Deno, and Hyperdrive do not yet have the same public integration
  evidence as mature competitors.
- Cossack provides schema metadata for Studio integration, not a standalone
  database GUI in this package.

These are acceptable tradeoffs only when Cossack's focused model is useful to
the application. If an alternative already fits the preferred architecture,
its maturity is a substantial reason to use it.
